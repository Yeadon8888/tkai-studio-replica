# PDCA：每一条视频、每一个品都走一遍

| 阶段 | 做什么 | 谁负责 | 产出 | 出口条件 |
|---|---|---|---|---|
| **Plan 计划** | 选品、写产品卡、框定产品事实、选对标、定档位、分条数、写简报 | agent 起草，用户确认范围与预算 | `product.json`、`product_anchor.txt`、`product_facts`、简报 | 产品卡已确认；预算在上限内；每条简报有锚点与档位 |
| **Do 执行** | 按简报生成视频（H/M/L 来自裂变，X 来自自写脚本） | 生成接口（MiniMax H3） | 成片、任务记录 | 成片落盘，ffprobe 核验通过 |
| **Check 检查** | 机器检查 → 三位专家逐项判定 → 闸门 → 合规关 → 人工抽查 | 计算型 + 专家 + 人 | `reviews/*.json`、判定、看板 | 通过闸门且合规全过；或明确判为不通过并写明原因 |
| **Act 改进** | 按失败原因退回 → 修提示词或规则 → 把结论写回对标与产品事实 | agent 提出，人批准规则变化 | 新简报 attempt、规则候选、校准记录 | 同一缺陷不再连续出现；规则变化经人批准 |

## 每个阶段的关键规则

**Plan**
- 产品事实没有确认的，不写进提示词。
- 条数与预算在动手前确认。超出默认预算先沟通。

**Do**
- 同一条简报只允许一个在途任务。未结束的任务先查原任务，不重提。
- 生成前检查调用上限（Gemini 每运行 100 次，TikHub 每次查询 100 次）。

**Check**
- 先算后判：机器检查不过，不交给专家，直接退回。
- 专家的每一个不合格判断都要有时间码和具体描述，否则不计入。
- 通过闸门 ≠ 交付。人工抽查覆盖每个新方向的前几条（H1 试样）。

**Act**
- 退回的阶段由原因决定（见 `config/rubric.yaml` 的 causes），不要一律重做全片。
- 同一缺陷连续两次未解决，停止自动重做，交给人（H2）。
- 人工判定与专家结论不一致时，记入校准（`kit/calibrate.py`），再决定是否改专家提示词。专家提示词与评分标准的改动必须经人批准。

## 循环在哪里闭合

```
Plan ──► Do ──► Check ──► Act
 ▲                          │
 └──── 规则与提示词更新 ◄─────┘   （只在人批准后生效）
```

每一轮记录：本轮范围、预算、通过/不通过及原因、改了什么规则。下一轮从记录开始，不从记忆开始。
