# 拆解的读法、生成—审判—修订循环

## 一、拆解：借 Hypit 的读法（不再用一个固定问卷）

Hypit 的参考视频读法（`~/.claude/skills/hypit/references/creation/reference-video.md`）分三步：

1. **先整体看**：看完整条，找出钩子、论证或故事、注意力的转移、回报，以及观众应有的反应。读出台词和时间。
2. **再逐段细看**：每个关键镜头写清"内容、位置、入场、停留、出场"，并说明这个选择对观众做了什么（建立人物、对比、积累证明、放大反应、让过程清楚、把注意力交给下一步）。
3. **最后分出保留与重做**：哪些关系在换人、换产品、换文案后必须保留，哪些可以重新设计。

我们的做法（对应 `kit/loop.py` 的拆解步骤）：
- 整体读：Gemini 看公开视频链接，输出整体结构与钩子。
- 逐段读：把整条视频交给理解模型，按实际时间码细看画面并听声音；只有禁止临时上传且没有公网地址时才回退抽帧。
- 保留与重做：直接映射到档位。**固定项（保留）= 复刻的依据**；**变化项（重做）= 裂变的自由度**。H 档只换人物和产品，M/L 档换得更多，X 档不参考对标。

限制：
- 语音转写（逐字时间）还没有确认的模型（`CLAUDE.md` 标为"待确认"）。在确认之前，台词时间只能靠 Gemini 读视频得到，精度较低。
- 不使用 creatok 的 analyze / recreate：它需要单独的 `CREATOK_API_KEY` 和 `creatok` 命令，属于 TikHub、TokensFactory 之外的付费服务，需要你单独批准。

## 二、生成—审判—修订循环（`kit/refine_loop.py`）

```
基础简报 ──► 预算检查 ──► 生成（MiniMax H3）──► 审判（机器检查 + 三位专家 + 闸门）
                                                        │
                                  通过 ◄────────────────┤
                                                        ▼
                               升级/轮数用完 ◄── 否 ──► 问题清单（专家问题 + 退回原因的修改方向）
                                                        │
                                                        ▼
                                  Gemini 修改提示词（只改问题涉及的部分，锚点逐字、固定项不变）
                                                        │
                                                        ▼
                                  硬约束检查（锚点、长度、非空）不过 → 重试一次 → 仍不过则停止
                                                        │
                                                        └──► 新简报，回到"预算检查"
```

规则：
- **Gemini 只写提示词文字**。通过与否由审判决定，锚点与固定项由代码检查，不由模型决定。
- **每一轮都要预算检查**。一条 10 秒视频约 1.3 元。默认每品 5 元，只够约 3 轮；超出就停止并交给人。
- **轮数上限**只读 `.env` 的 `MAX_ATTEMPTS`，默认 3；达到上限就停止并交给人。
- **同一缺陷连续两次出现**（相邻两轮的否决项或专家 issue cause 有交集），状态记为 `repeat_defect`，不再修订。
- 每一轮的提示词哈希、判定、加权分、低分维度、否决项都写入 `<运行目录>/refine/<基础简报>.jsonl`。
- 修改记录只能追加，不删除旧轮次。

### 多段成片

生成服务一次只生成一段时，在简报里使用 `segments`。每一段必须有自己的提示词和时长，参考图可省略；省略时继承简报顶层的 `images`：

```json
{
  "id": "TSP-20s",
  "images": ["refs/product.png"],
  "resolution": "768p",
  "aspect_ratio": "9:16",
  "segments": [
    {"prompt": "前 10 秒：举起试纸瓶，再把试纸蘸入水中。", "duration": 10},
    {"prompt": "后 10 秒：拿起试纸，与瓶身色卡逐项对照。", "duration": 10}
  ]
}
```

`loop gen` 会把它展开为 `<id>-s1`、`<id>-s2` 等独立任务。所有段成功后，ffmpeg 会统一分辨率、帧率和音轨，再输出 `takes/<id>.mp4`；任一段失败或拼接失败都不会留下父成片，已成功的分段仍保留，后续重跑也不会重复提交已落盘的段。评审只看拼好的整条视频，机器检查的目标时长是各段时长之和。

修订时，带时间码的问题会落到对应段。下一轮只修改并重新生成命中的段，其余段直接复用上一轮文件，再重新拼接和评审；问题没有可解析时间码时，为避免漏改，会修订全部段。

费用按实际生成秒数计算，而不是按成片条数计算。例如 2 段 × 10 秒按 20 秒计费；修订只重生成其中一段时，只新增该段秒数的费用。每个付费轮次仍须先通过品级预算检查。

## 三、三类提示词的来源（现状）

| 类别 | 现在 | 计划 |
|---|---|---|
| H/M/L 初稿 | 代码按对标固定项拼接 | 保留代码拼接作为初稿，再进入循环 |
| X 初稿 | agent 手写，经计算型自检 | Gemini 按模板起草，经计算型自检 |
| 修订 | 无 | Gemini 按审判问题修改，受硬约束 |
| 专家评分标准 | 手写（`experts.yaml`） | 人批准后才改，模型只能提建议 |
